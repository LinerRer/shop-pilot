# ShopPilot 技术方案设计

版本 v2.0，2026-10-13

## 设计原则

1. 垂直领域优先，不做通用 NL2SQL——内置电商指标和归因路径，这是和通用工具的核心区别
2. 工具全部 MCP 化——数据查询和评论分析是独立 MCP Server，Agent 只做决策，工具能被别的客户端复用
3. 确定性逻辑不交给 LLM——指标公式、异常阈值用 Python 写死，LLM 只理解意图、调工具、读结果、组织语言
4. 数据工具只读——Agent 碰不到写操作
5. 可回溯——每次工具调用写 Trace 日志，体检结果入库

## 技术选型

| 层 | 技术 | 为什么选 |
|----|------|---------|
| 语言 | Python 3.11 | AI 生态 |
| Agent | LangGraph create_react_agent | 开箱即用的 ReAct 循环，支持并行工具调用；比手写状态机稳定，项目初期优先用成熟方案 |
| LLM | DeepSeek deepseek-chat | 便宜，中文好，支持 Function Calling |
| 工具协议 | MCP 1.30.0 (FastMCP) | 行业标准；2.x API 变了且资料少，锁 1.x |
| 数据库 | SQLite + SQLAlchemy 2.0 | 零部署，单文件，方便 mock |
| 数据处理 | pandas | 指标聚合 |
| 评论聚类 | LLM 直接聚 | 省掉 embedding 模型下载调试，DeepSeek 中文聚类够用 |
| 前端 | Streamlit + Plotly | 快；流式输出靠 nest_asyncio |
| 日报 | python-docx | 出 Word |
| API | FastAPI + uvicorn | Agent 能力服务化 |
| 定时 | APScheduler | 每天 8 点自动跑 |
| 配置 | pydantic-settings + .env | 阈值和路径集中管理 |
| 可观测 | 自研文件 Trace | 轻量，不依赖外部服务 |

### 为什么用 create_react_agent 而不是手写 StateGraph

原计划是手写 LangGraph 状态机（understand → router → attribution 循环），但实际评估后换了：手写状态机要自己管工具调用循环、错误重试、步数限制，调试成本高。`create_react_agent` 是官方封装的稳定 ReAct 循环，还自带 parallel tool calling。面试讲 ReAct（Reasoning + Acting，模型自主决定调哪个工具）一样有深度。

## 架构

```
接入层：Streamlit（流式问答/体检/图表） + FastAPI（/api/ask 等）
            │
            ▼
Agent 层：DeepSeek + LangGraph ReAct
  对话：HumanMessage → LLM 决策 → 调 MCP 工具 → 继续或回答
  体检：SystemMessage(归因规则) → scan_anomalies → 并行 get_product_detail
        + cluster_reviews → 归因报告
  特性：astream_events 流式输出、并行工具调用、Trace 日志
            │ MCP (stdio)
    ┌───────┴───────┐
    ▼               ▼
ecomdb Server    review Server
7个数据工具       cluster_reviews（LLM 差评聚类）
    │               │
    └───────┬───────┘
            ▼
    SQLite：products / orders / order_items / traffic /
            reviews / refunds / daily_reports
            │
            ▼
    定时任务(APScheduler) → 日报 → webhook 推送
    Trace 日志(logs/)、配置集中(config.py)、历史入库
```

## 数据库

7 张表：products、orders、order_items、traffic（按天×渠道×商品）、reviews、refunds、daily_reports（日报历史，工程化阶段加的）。

Mock 数据用 `random.seed(42)` 保证可复现，45 天，8 商品 5 渠道。3 个预埋异常在 verify.py 里能验证：P1008 物流破损后订单腰斩差评率 40%、P1004 直播 UV 581、P1006 断货后 0 单。

## MCP Server

### ecomdb_server.py（7 个工具，只读）

| 工具 | 作用 |
|------|------|
| list_products | 列商品 ID 和名称 |
| get_metrics | 指定日期范围的全量指标 + 环比 |
| get_trend | 指标按天趋势 |
| get_channel_breakdown | 各渠道 UV/GMV/转化率 |
| get_product_ranking | 商品销量/GMV/退款排行 |
| get_product_detail | 单商品详情 + 指标 + 差评样例，归因下钻用 |
| scan_anomalies | 确定性阈值扫描全店异常，体检第一步必调 |

### review_server.py（1 个工具）

`cluster_reviews(product_id, days=14)`：从 DB 读差评，截断 3000 字后发给 DeepSeek，要求输出严格 JSON 的主题聚类。Prompt 约束主题名要具体（"物流破损""漏水"），禁止"其他问题"这种泛泛的标签。

没上 embedding + KMeans，因为项目初期优先保证主链路跑通，LLM 直接聚效果够用。

## Agent 设计（ReAct）

体检的工作流：

```
SystemMessage（归因规则 + 流程约束）
  → HumanMessage("做一次体检")
  → LLM 第 1 轮：调 scan_anomalies
  → 拿到异常清单
  → LLM 第 2 轮：并行调 get_product_detail(多个异常商品)
                + cluster_reviews(差评率高的商品)
  → 拿到详情和聚类
  → LLM 第 3 轮：综合数据，输出归因报告
```

Prompt 里的硬约束：
- 第一步必须调 scan_anomalies（保证召回，不依赖 LLM 自己发现）
- high 级异常必须下钻 get_product_detail
- 差评率高的必须调 cluster_reviews
- 所有结论必须来自工具返回，禁止编数字
- 归因规则内置：库存 0 = 断货、差评主题破损 = 物流、差评主题质量 = 商品问题

## 关键工程问题

### 1. 怎么防止大模型编数字

指标计算和异常阈值全部在 metrics.py 用 Python 写死。LLM 不自己算 GMV，只引用工具返回的数字。体检报告末尾注明"所有数字来自工具返回"。这是这个项目最核心的设计决策。

### 2. Streamlit + 异步 Agent 的 Event loop closed

报错：`RuntimeError: Event loop is closed`。

原因：Streamlit 脚本是同步的，第一次 `asyncio.run()` 后事件循环关闭，MCP 的 stdio 连接绑死在已关闭的循环上，第二次调用就炸。

解决：问答流式用 `nest_asyncio.apply()` 让循环可重入，主线程直接 `asyncio.run()` + `astream_events()`；体检（非流式）用 `ThreadPoolExecutor` 放独立线程，每个线程全新事件循环。

### 3. MCP 2.x 版本陷阱

默认 `pip install mcp` 装到 2.x，FastMCP 改名 MCPServer，API 全变，资料少。锁 `mcp==1.30.0`（`pip install "mcp<2"`）。

### 4. 异常召回不稳定

一开始纯靠 LLM 自主发现异常，会漏掉 P1006 断货——它差评率不高但 GMV 跌了，LLM 不一定关联到库存。加了确定性 `scan_anomalies` 工具，阈值写死（GMV 跌 ≥30% 且库存 0 = 疑似断货），Agent 第一步必须先调它。召回从"看 LLM 心情"变成稳定 100%。

### 5. 并行下钻

体检时多个 high 异常商品要调 get_product_detail。ReAct + DeepSeek 自动支持 parallel tool calling：一轮 AIMessage 里同时发起多个 tool_call，并行执行，耗时约等于最慢的一个。Trace 日志里能看到 3 个详情调用在同一轮发起。

### 6. 数据库相对路径

`sqlite:///data/shop.db` 相对路径依赖运行目录，PyCharm 运行和终端运行的工作目录不同，会报 `unable to open database file`。统一用 `Path(__file__).resolve().parents[2]` 算项目根的绝对路径。

### 7. GitHub push 被封

HTTPS 443 端口 Connection reset / timeout，手机热点也不行。改用 SSH 22 端口，生成 ed25519 密钥加到 GitHub，远程地址改成 `git@github.com:LinerRer/shop-pilot.git`，一次成功。
