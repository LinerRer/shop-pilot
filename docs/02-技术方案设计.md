## 0. 设计原则

1. **垂直优先，不做通用工具**：Agent内置电商指标体系和归因决策树，这是和通用NL2SQL产品（WrenAI/Vanna）的核心差异。
2. **能力全部MCP化**：数据查询、评论分析、报告生成作为独立MCP Server，Agent只负责决策编排，工具可被任意MCP客户端复用。
3. **确定性逻辑不交给LLM**：指标公式、异常阈值用Python硬编码保证100%正确；LLM只负责意图理解、SQL生成、归因推理、报告措辞。
4. **只读安全边界**：所有数据工具只读，SQL白名单拦截写操作。
5. **可评估、可观测**：从第一天接入Langfuse，并准备50题测试集量化准确率。

## 1. 技术选型

### 1.1 技术栈

| 层级 | 技术 | 选型理由 |
|------|------|---------|
| 语言 | Python 3.11 | AI生态完善 |
| Agent编排 | LangGraph | 有向状态机，支持条件分支、循环、人工中断，适合归因排查这种需要动态决策路径的场景 |
| LLM | DeepSeek V3 (deepseek-chat) | 便宜（输入¥1/百万token）、支持Function Calling、中文好 |
| 工具协议 | MCP Python SDK (`mcp`) | 2026行业标准，S级项目核心加分项 |
| 数据库 | SQLite | 零部署、单文件、方便mock和演示 |
| ORM | SQLAlchemy | 方便建表和生成mock数据 |
| 数据处理 | Pandas | 指标计算、透视、聚合 |
| 本地Embedding | sentence-transformers + bge-small-zh-v1.5 | 离线免费、中文效果好、模型仅~100MB |
| 聚类 | scikit-learn (KMeans/HDBSCAN) | 差评语义聚类 |
| 可视化 | Plotly | 交互式图表，可嵌入Streamlit和报告 |
| 报告生成 | python-docx | 生成Word运营日报 |
| 前端 | Streamlit | 快速搭建对话+图表界面 |
| 可观测 | Langfuse | 开源、LangGraph原生集成 |
| 配置 | pydantic-settings + .env | 类型安全 |

### 1.2 为什么是LangGraph

归因分析不是固定线性流程：Agent发现UV下降要去查渠道，发现差评突增要去做评论聚类，路径是动态的、可能反复迭代。LangGraph的条件边和循环正好支持这种"边排查边决策"的模式，而CrewAI的线性任务队列和AutoGen的自由对话都不适合。

### 3.2 Mock数据策略

- 时间跨度：最近90天
- 规模：约20个商品、5个品类、5个渠道、约2万订单、1.2万评论、2千退款
- **预埋异常案例**（供异常检测演示）：
  1. 某商品第75天起因物流破损问题，差评和退款激增、销量下滑
  2. 某商品某天直播渠道流量暴涨（营销活动）
  3. 某商品库存售罄导致UV正常但转化归零
  4. 某品类整体季节性下滑
- 评论内容：基于模板+随机组合生成真实感中文评论（好评/中评/差评，差评覆盖物流、质量、尺码、色差、客服等主题）

## 4. MCP Server设计

### 4.1 EcomDB Server（数据查询，只读）

| 工具 | 入参 | 返回 | 说明 |
|------|------|------|------|
| `get_metrics` | date_range, metrics[] | 指标值字典 | 计算GMV/订单数/客单价/转化率/退款率等 |
| `get_trend` | metric, granularity, days | 时间序列 | 指标趋势，含环比 |
| `get_channel_breakdown` | date | 各渠道UV/转化 | 渠道维度拆解 |
| `get_product_ranking` | date_range, order_by, top_n | 商品排行 | 销量/退款/差评排行 |
| `query_sql` | sql | 查询结果 | 兜底：执行只读SELECT（白名单校验） |

**SQL安全：** `query_sql`用正则+SQL解析校验，只允许SELECT开头、禁止INSERT/UPDATE/DELETE/DROP/ATTACH，强制加LIMIT。

### 4.2 Review Server（评论分析）

| 工具 | 入参 | 返回 |
|------|------|------|
| `get_rating_stats` | date_range, product_id? | 评分分布、好评率/差评率 |
| `get_reviews` | date_range, rating?, product_id?, limit | 评论列表 |
| `analyze_sentiment` | date_range | 情感分布统计 |
| `cluster_negatives` | date_range, n_clusters | 差评聚类：主题标签+数量+典型评论 |

### 4.3 Report Server（图表与报告）

| 工具 | 入参 | 返回 |
|------|------|------|
| `make_chart` | chart_type, data, title | 图表文件路径（PNG/HTML） |
| `export_daily_report` | report_data | Word文件路径 |

## 5. LangGraph工作流设计

### 5.1 对话工作流（取数/归因/评论）

```
START
  → understand   LLM意图识别，输出intent + 实体（时间/商品/指标）
  → router       条件路由
      ├─ query    → get_metrics/get_trend → answer
      ├─ attribute→ detect → attribution循环 → answer
      ├─ review   → sentiment/cluster → answer
      └─ report   → 跳转日报工作流
  → answer        结合数据生成中文回答（带数字、结论、建议）
END
```

### 5.2 归因循环（核心技术点）

状态中维护`investigation_trace`（排查路径记录）和`hypotheses`（待验证假设）：

```
detect（找出异常商品/指标）
  → attribution_plan（LLM根据归因决策树列出待排查假设）
  → verify_hypothesis（逐个调用MCP工具验证：查UV?查渠道?查评论?查库存?）
  → judge（LLM判断：假设成立? 需要继续排查?）
      ├─ 需继续且未超步数 → verify_hypothesis（循环）
      └─ 已定位根因/超5步 → conclude（输出归因结论+建议）
```

最大排查步数硬限制5步，防止无限循环和token失控。

### 5.3 日报工作流

```
START → collect_metrics（昨日+环比指标）
      → detect_anomalies（全商品扫描）
      → attribute_each（对Top异常自动归因，复用归因循环）
      → review_insights（差评聚类Top5）
      → build_charts（趋势图/占比图/渠道图）
      → compose_report（LLM生成结论与建议）
      → export_docx（Report MCP生成Word）
END
```

### 5.4 状态定义（核心字段）

```python
class ShopState(TypedDict):
    messages: list              # 对话历史
    intent: str                 # query/attribute/review/report/chitchat
    entities: dict              # {date_range, product, metrics, channel}
    query_results: list         # 工具返回的数据
    anomalies: list             # 检出的异常
    investigation_trace: list   # 归因排查路径
    hypotheses: list            # 待验证假设
    attribution_steps: int      # 已排查步数
    conclusion: str             # 归因结论
    charts: list                # 图表路径
    report_path: str            # 报告路径
```

## 6. 关键工程问题

### 6.1 如何保证NL2SQL正确率？
- Prompt中注入完整表结构、字段含义、3个few-shot示例
- 指标类问题优先走确定性的`get_metrics`工具（Python算），只有复杂灵活查询才走`query_sql`
- SQL执行失败时把报错回传LLM自动修正，最多重试2次
- 用50题测试集持续验证，错误case补充进few-shot

### 6.2 如何让归因不"瞎猜"？
- system prompt内置第3节的归因决策树，强制Agent按路径取数验证
- 每个结论必须有对应数据支撑（要求LLM输出引用了哪些数据）
- 排查路径记录在investigation_trace中，可在界面展示"思考过程"

### 6.3 评论聚类怎么做？
- 用bge-small-zh对差评生成embedding
- KMeans聚类（k用轮廓系数自动选择，范围3-8）
- 每个簇取离质心最近的3条评论，让LLM生成主题标签（如"物流破损"）

### 6.4 Token成本控制
- 取数结果只传聚合后的小表，不传原始明细
- 评论聚类在本地用embedding完成，不把全部评论发给LLM；只把每簇代表性评论发给LLM打标签
- 归因循环步数上限5，日报归因只处理Top3异常

### 6.5 可观测
- Langfuse记录每个节点的输入输出、每次工具调用、token与耗时
- 归因链路在Langfuse中形成可回放的trace树
