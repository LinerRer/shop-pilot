## 0. 设计原则

1. **垂直优先，不做通用工具**：Agent内置电商指标体系和归因决策树，和通用NL2SQL产品形成差异。
2. **能力全部MCP化**：数据查询、评论分析作为独立MCP Server，Agent只负责决策编排，工具可被任意MCP客户端复用。
3. **确定性逻辑不交给LLM**：指标公式、异常阈值用Python硬编码保证100%正确；LLM只负责意图理解、归因推理、报告措辞。
4. **只读安全边界**：所有数据工具只读，Agent无法修改业务数据。
5. **可观测、可回溯**：每次Agent工具调用写Trace日志，体检结果入库。

## 3. 数据库设计

### 3.1 表结构（7张表）

**products（商品表）**：product_id / name / category / price / cost / stock / status

**orders（订单表）**：order_id / user_id / amount / status / channel / create_time

**order_items（订单明细）**：id / order_id / product_id / quantity / unit_price

**traffic（流量表，按天×渠道×商品）**：id / date / channel / product_id / uv / pv / add_cart

**reviews（评论表）**：review_id / product_id / order_id / rating / content / create_time

**refunds（退款表）**：refund_id / order_id / product_id / amount / reason / create_time

**daily_reports（日报历史表，工程化新增）**：id / report_date / anomaly_count / high_count / anomalies_json / root_cause / created_at

### 3.2 Mock数据策略

- 时间跨度：最近45天（以运行当天为基准，可复现：random.seed(42)）
- 规模：8个商品、5个渠道、约4100订单、2300评论、210退款、1800流量记录
- **3个预埋异常**（供异常检测演示）：
  1. P1008保温杯第35天起物流破损：转化率×0.45、差评权重升高、退款率26%、差评内容含破损/漏水
  2. P1004耳机第20天直播渠道UV×7（正面异常，营销活动）
  3. P1006台灯第40天起断货：转化率0、stock=0、status="已售罄"
- 评论内容：基于模板+随机组合生成中文评论，差评覆盖物流/质量/尺码/色差等主题

## 4. MCP Server设计

### 4.1 ecomdb_server.py（数据查询，只读，7个工具）

| 工具 | 入参 | 返回 | 说明 |
|------|------|------|------|
| `list_products` | 无 | 商品列表 | 列出所有商品ID和名称 |
| `get_metrics` | start_date, end_date, product_id? | 指标字典 | GMV/订单/客单价/UV/转化率/加购率/退款率/差评率+环比 |
| `get_trend` | metric, days | 时间序列 | 指标按天趋势 |
| `get_channel_breakdown` | date? | 各渠道UV/GMV/转化 | 渠道维度拆解 |
| `get_product_ranking` | metric, period, top_n | 商品排行 | 销量/GMV/退款排行 |
| `get_product_detail` | product_id, days | 商品详情+指标+差评样例 | 归因下钻用 |
| `scan_anomalies` | 无 | 异常清单 | 确定性阈值扫描全店异常（核心工具） |

### 4.2 review_server.py（差评主题聚类，1个工具）

| 工具 | 入参 | 返回 | 说明 |
|------|------|------|------|
| `cluster_reviews` | product_id, days=14 | 主题列表 | 从数据库读差评→LLM聚类→输出{theme, count, samples} |

**聚类实现**：不使用embedding+KMeans（7天冲刺省掉模型下载），直接把差评文本（截断3000字）发给DeepSeek，要求输出严格JSON的主题聚类。Prompt约束主题名简短具体（如"物流破损""漏水"），禁止泛泛的"其他问题"。

## 5. Agent设计（ReAct模式）

### 5.1 为什么用 create_react_agent 而非手写状态机

原计划手写LangGraph StateGraph（understand→router→attribution循环），但7天冲刺中评估：
- 手写状态机需要自己管理工具调用循环、错误重试、步数限制，调试成本高
- `create_react_agent` 是LangGraph官方封装的ReAct循环，稳定可靠，开箱即用
- 支持parallel tool calling（体检时3个商品详情并行调取）
- 面试时讲"ReAct=Reasoning+Acting，模型自主决定调哪个工具"同样有技术深度

### 5.2 体检工作流

```
SystemMessage(归因规则+流程约束)
  → HumanMessage("请做一次体检")
  → LLM第1轮：决定调 scan_anomalies
  → 拿到异常清单
  → LLM第2轮：决定并行调 get_product_detail(P1003/P1006/P1008)
            + cluster_reviews(P1008) 等
  → 拿到详情和聚类
  → LLM第3轮：综合数据，输出归因报告
```

### 5.3 关键Prompt约束

- 第一步必须调 scan_anomalies（确定性扫描，保证召回）
- 对high级异常必须下钻 get_product_detail
- 差评率高的商品必须调 cluster_reviews
- 所有结论必须来自工具返回，禁止编造数字
- 归因规则内置：库存0=断货、差评主题破损=物流、差评主题质量=商品问题

## 6. 关键工程问题与解决方案

### 6.1 如何防止大模型编数字？

**确定性与LLM分层**：
- 指标计算、异常阈值判断全部在 `metrics.py` 用Python写死
- LLM只负责：理解问题、决定调哪个工具、读工具返回、组织语言给建议
- LLM永远不自己算GMV，只引用工具返回的数字
- 体检报告末尾注明"所有数字来自工具返回，未做推算"

### 6.2 Streamlit + 异步Agent 的 Event loop closed 问题

**问题**：Streamlit脚本是同步的，直接用 `asyncio.run()` 调异步Agent，第一次调用后事件循环关闭，MCP的stdio连接绑死在已关闭的循环上，第二次报 `RuntimeError: Event loop is closed`。

**解决方案**：
- 问答流式输出：用 `nest_asyncio.apply()` 让事件循环可重入，在主线程直接 `asyncio.run()` + `astream_events()` 流式逐字输出
- 体检（非流式）：用 `ThreadPoolExecutor` 把每次调用放进独立线程，每个线程用全新事件循环，互不干扰

### 6.3 MCP 2.x 版本陷阱

**问题**：默认 `pip install mcp` 装到2.x，FastMCP被改名MCPServer、API全变、资料少。

**解决方案**：锁定 `mcp==1.30.0`（`pip install "mcp<2"`），使用稳定的FastMCP接口。

### 6.4 并行下钻优化

体检时需要对多个high异常商品调 get_product_detail。ReAct + DeepSeek 自动支持 parallel tool calling：在一轮AIMessage中同时发起多个tool_call，工具并行执行，耗时≈最慢的一个而非N倍。Trace日志可证3个详情调用在同一轮发起。

### 6.5 数据库相对路径问题

**问题**：`sqlite:///data/shop.db` 相对路径依赖运行目录，在不同入口（PyCharm运行/终端/Streamlit）下可能找不到文件。

**解决方案**：用 `Path(__file__).resolve().parents[2]` 计算项目根目录的绝对路径，所有入口一致。

### 6.6 异常召回稳定性

**问题**：纯靠LLM自主发现异常，可能漏掉断货这类"差评率不高但GMV跌"的异常。

**解决方案**：加确定性 `scan_anomalies` 工具，阈值写死在代码里（GMV跌≥30%且库存0=疑似断货），Agent第一步必须先调它拿到异常清单，再下钻归因。召回从"看LLM心情"变成"100%稳定"。
